# Тест-план: Swag Labs

| | |
|---|---|
| Объект | Веб-приложение Swag Labs, https://www.saucedemo.com/ |
| Версия | Публичная версия сайта на дату тестирования |
| Тип тестирования | Ручное, функциональное и UI, черный ящик |

## 1. Цель

Проверить основной пользовательский путь интернет-магазина (вход → каталог → корзина → оформление заказа), найти дефекты и оформить их так, чтобы разработчик мог воспроизвести их без уточняющих вопросов.

## 2. Что тестируется

| Модуль | Функции |
|---|---|
| Логин | Вход, сообщения об ошибках, заблокированный пользователь, доступ к страницам без авторизации |
| Каталог | Список товаров, сортировка, карточка товара |
| Корзина | Добавление и удаление, счетчик на иконке, сохранение состояния |
| Оформление заказа | Форма данных покупателя, обзор заказа, расчет суммы, завершение |
| Меню | All Items, About, Logout, Reset App State |
| Интерфейс | Отображение элементов, адаптивность от 320 px, кроссбраузерность |

## 3. Что не тестируется

| Что | Почему |
|---|---|
| Нагрузка и производительность под нагрузкой | Публичный учебный сайт, нагрузка на него недопустима |
| Безопасность (пентест) | Вне рамок ручного функционального тестирования |
| Реальная оплата и доставка | В приложении их нет, оформление заказа имитационное |
| Внешние ссылки (Sauce Labs, соцсети) | Сторонние ресурсы, проверяется только то, что ссылка открывается |

## 4. Подход и виды тестирования

| Вид | Что делаем |
|---|---|
| Smoke | Вход `standard_user`, добавление товара, оформление заказа. Если путь не проходит, дальнейшее тестирование блокируется |
| Функциональное | Тест-кейсы по модулям: позитивные, негативные, граничные |
| Сравнительное | Повтор ключевых сценариев под `problem_user`, `error_user`, `visual_user`, `performance_glitch_user` и сравнение с `standard_user` |
| UI | Тексты, изображения, выравнивание, состояния кнопок |
| Совместимость | Desktop Chrome, Firefox, Edge; мобильная эмуляция в DevTools (320 px, 375 px, планшет) |
| Исследовательское | Сессии по 30–60 минут с заранее заданной целью |

Техники тест-дизайна: классы эквивалентности, граничные значения, таблица решений, переходы состояний. Примеры в [test-design](../test-design/README.md).

## 5. Источник ожидаемого результата

Спецификации к Swag Labs нет. Ожидаемый результат определяется по:

1. поведению `standard_user` как эталона;
2. тексту и элементам интерфейса (например, если есть пункт сортировки «Price (low to high)», товары должны идти по возрастанию цены);
3. общепринятому поведению интернет-магазинов (нельзя оформить заказ из пустой корзины, удаленный товар исчезает из корзины).

Спорные случаи отмечаются в баг-репорте как вопрос к требованиям.

## 6. Окружение

| Параметр | Значение |
|---|---|
| ОС | Windows 11 |
| Браузеры | Google Chrome, Mozilla Firefox, Microsoft Edge (актуальные версии, точная версия указывается в каждом баг-репорте) |
| Мобильная эмуляция | Chrome DevTools, Device Mode |
| Тестовые данные | Учетные записи со страницы входа, пароль `secret_sauce` |

## 7. Критерии

**Начало тестирования:** сайт доступен, вход под `standard_user` работает.

**Приостановка:** smoke-тест не проходит (не удается войти или оформить заказ под `standard_user`).

**Завершение:**
- выполнены все тест-кейсы с приоритетом High;
- каждый найденный дефект оформлен баг-репортом;
- результаты сведены в отчет.

## 9. Риски

| Риск | Что делаем |
|---|---|
| Нет требований, ожидаемое поведение спорное | Опираемся на источники из раздела 5, спорное помечаем как вопрос |
| Сайт может обновиться, и баг перестанет воспроизводиться | В каждом баг-репорте фиксируем дату, браузер и скриншот |
| Состояние корзины хранится в браузере и влияет на тесты | Перед каждым тест-кейсом: Reset App State или очистка localStorage |
